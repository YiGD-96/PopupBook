# 팝업북 성능 최적화 정리

> 2026-10-17 ~ 10-18 · 커밋 `b24bd00` (`claude/perspective-hardback`)
> 대상: 「당근을 따라, 구좌」 3D 팝업북 (React 19 · three.js / R3F · GSAP)

배경을 밤의 호두나무 책상으로 바꾼 뒤 "렉이 많아졌다", "책장 넘김이 끊긴다"는 문제가 생겼다. 원인을 측정으로 하나씩 찾아 고쳤고, 이어서 로딩까지 다듬었다.

---

## 한눈에 보기

| 항목 | 이전 | 이후 |
|---|---|---|
| 책장 넘김 끊김 (1920×1080, 125%) | 넘길 때마다 1번 이상 | **0번** |
| 한 프레임 GPU 시간 (1920×1080, 125%) | 11.4 ms | **8.1 ms** |
| 가만히 볼 때 GPU 사용량 | 초당 약 680 ms | **초당 약 250 ms** |
| 큰 화면·느린 CPU에서 가만히 볼 때 끊김 (3초) | 15번 | **0번** |
| 큰 화면·느린 CPU에서 넘길 때 끊김 | 37번 / 26번 | **12번 / 4번** |
| 휴대폰·느린 CPU에서 넘길 때 끊김 | 8번 / 5번 | **3번 / 2번** |
| 첫 화면이 보이기까지 (9 Mbps) | 0.69 ~ 1.17초 | **0.40초** |
| 책을 읽을 수 있기까지 (9 Mbps) | 8.7초 | **7.3초** |
| 책을 읽을 수 있기까지 (빠른 연결) | 6.8초 | **5.7초** |

- "큰 화면"은 2560×1440(150%), "느린 CPU"는 CPU 4배 느림 조건이다.
- 측정 PC의 GPU는 Intel Iris Xe(내장)다.

## 1. 먼지 효과 제거

**증상:** 책상 배경을 넣은 뒤 전체적으로 버벅임.

**원인:** 화면 위를 떠다니던 먼지 18개. 흐림 필터가 걸린 애니메이션이라 매 프레임 캔버스 위에서 다시 합성됐다. 책상을 넣기 전 버전과 비교하니, CPU 4배 느림 조건에서 프레임 시간이 두 배가 됐다.

**조치:** 먼지만 뺐다. 책상 자체는 그대로 두었다. 측정해 보니 책상은 원인이 아니었다.

## 2. 책장 넘김 끊김 (1차)

### 원인 찾기
CPU 프로파일로 넘김 한 번을 처음·중간·끝으로 나눠 봤다.

| 구간 | 무엇이 시간을 썼나 |
|---|---|
| 시작 | 넘기는 종이의 셰이더 컴파일 (`getProgramInfoLog`) |
| 중간 | 매 프레임 셰이더 설정 재선택 (`getParameters`·`getProgram`·`getProgramCacheKey`, 합계 약 200 ms) |
| 끝 | 들어온 카드를 버리고 새로 만듦, 다음 장 미리 받기가 바로 시작됨 |

결정적인 것은 **"투명 + 양면" 재질**이었다. three.js는 이런 재질을 매 프레임 뒷면·앞면 두 번 그리면서 셰이더 설정을 다시 고른다. 카드 18장이면 초당 2천 번이 넘는다. 넘길 때뿐 아니라 가만히 있을 때도 그랬다.

### 조치

| 조치 | 내용 | 파일 |
|---|---|---|
| 카드를 한 번에 그리기 | `forceSinglePass`. 카드는 평평한 오려낸 그림이라 결과는 같다 | `bookParts.tsx` (`cardMaterial`, `Surface`), `standingBook.tsx` |
| 재질 공유 | 그림 하나에 재질 하나를 만들어 모든 카드가 함께 쓴다 (`WeakMap`) | `bookParts.tsx` (`cardMaterial`) |
| 셰이더 미리 준비 | 넘기는 종이는 시작할 때, 다음 장 카드는 펼침을 보는 동안 준비한다 | `bookParts.tsx` (`warmMaterials`, `sheetMaterials`) |
| 카드 유지 | 지금 장과 들어오는 장의 카드를 한 그룹에 장 번호 키로 두어, 넘김이 끝나도 다시 만들지 않는다 | `Storybook.tsx` |
| 종이 휘어짐 계산 | 배열을 직접 계산한다. 결과는 이전과 비트 단위까지 같고, 0.215 → 0.081 ms로 2.7배 빠르다 | `paperGeometry.ts` |
| 미리 받기 시점 | 다음 장 미리 받기를 카드가 다 선 뒤 0.7초 후에 시작한다 | `Storybook.tsx` (`warmChapter`) |

**결과**
- 1920×1080 (125%): 넘김 2번 모두 끊긴 프레임 0.
- 2560×1440 (150%), CPU 2배 느림: 시작과 끝에 33 ms짜리 한 번씩만 남았다.

## 3. 전체 최적화 (2차)

### 3-1. GPU 비용 측정
부분별로 하나씩 꺼 가며 프레임당 GPU 시간을 쟀다 (1920×1080, 125%, 합계 11.4 ms).

| 부분 | 꺼서 줄어든 시간 |
|---|---|
| **책상** | **3.3 ms** (그중 비스듬한 텍스처 필터링 1.3 ms) |
| 가장자리 매끄럽게 (MSAA) | 2.4 ms |
| 카드 | 1.8 ms |
| 책 케이스 | 0.6 ms |
| 불투명 캔버스로 바꾸기 | 차이 없음 |

### 3-2. 책상은 한 번만 그린다 — `DeskBackdrop`
책상과 카메라는 읽는 동안 움직이지 않는다. 그래서 다음처럼 바꿨다.
- 창 크기나 카메라가 바뀔 때만 책상을 한 번 그린다.
- 그 그림을 WebGL 캔버스 **뒤의 2D 캔버스**(`.desk-backdrop`)에 복사해 둔다.
- 매 프레임은 책만 그린다.

브라우저가 투명한 책 캔버스를 그 위에 합성하는 방식은, GPU가 책상 위에 책을 그리던 방식과 같다. 그래서 가장자리까지 같은 모습이 나온다.

| 화면 | 이전 | 이후 |
|---|---|---|
| 1920×1080 (125%) | 11.4 ms | **8.1 ms** |
| 휴대폰 | 5.6 ms | **4.0 ms** |
| 2560×1440 (150%) | 15.2 ms | **13.9 ms** |

인트로 영상은 기존 `Desk`를 그대로 쓴다. 영상에서 책으로 넘어가는 장면은 이전과 같다.

### 3-3. 필요한 만큼만 그린다 — `FramePacer`
Canvas를 `frameloop="never"`로 두고, 언제 그릴지를 직접 정한다.

| 상황 | 그리는 횟수 |
|---|---|
| 넘김 · 팝업 · 드래그 · 애니메이션 중 | 매 프레임 (60 fps) |
| 펼침을 가만히 볼 때 (카드 흔들림만 있음) | **초당 30번**. 흔들림은 한 프레임에 0.5픽셀도 안 움직인다 |
| 글로 읽기가 책을 덮었을 때 | **0** |
| 인트로 영상 아래에서 준비하는 동안 | 0. 준비가 끝나면 한 프레임만 그린다 |

R3F의 `demand` 모드는 한 프레임 늦게 그려서 넘김이 30 fps로 떨어졌다. 그래서 `advance()`로 같은 프레임 안에서 바로 그린다.

### 3-4. 느린 GPU 안전장치 — `ResolutionGovernor`
대상은 내장 GPU에 큰 고해상도 화면(예: 4K, 150%)을 쓰는 경우다.
- 움직이는 동안 프레임의 1/5 이상이 늦는데 CPU는 한가하면(GPU가 병목이면), 해상도를 15%씩 낮춘다.
- 처음 해상도의 60% 아래로, 그리고 1× 아래로는 내리지 않는다. 다시 올리지도 않는다.
- 일반 화면(1920·2560)에서는 동작하지 않았다.
- 4K (150%)에서: 첫 넘김에서 늦은 프레임 24개가 나와 1.275×로 낮췄고, 다음 넘김에서는 8개였다.
- 테스트: `tests/frame-pacing.test.mjs`. 현재 상태는 캔버스의 `data-pacing` 속성에서 볼 수 있다.

### 3-5. 넘김을 더 가볍게

| 조치 | 효과 |
|---|---|
| 넘기는 종이를 내내 마운트해 두고 그림만 바꾼다 | 넘길 때마다 하던 준비가 없어진다 |
| `textureView`: `needsUpdate` 대신 자기 version만 올린다 | `needsUpdate`는 공유된 원본 그림을 매 넘김마다 GPU에 다시 올렸다 (휴대폰 배경막도 같았음) |
| 다음 장 페이지 그림은 ref에만 채운다 | 보고 있는 동안 책 전체가 React로 다시 그려지던 것을 없앴다 |
| fps 계산을 스토어 대신 DOM(`data-fps`)에 쓴다 | App 전체가 2초마다 다시 그려지던 것을 없앴다 |

## 4. 로딩

**문제:** 3D 책 코드(272 KB)와 첫 장 그림이 **인트로 영상이 끝난 뒤에야** 받아지기 시작했다. 영상 다운로드가 끝난 뒤 약 3.6초 동안 네트워크가 놀았다. 또 Google Fonts CSS가 첫 화면을 최대 1초 막고 있었다.

| 조치 | 내용 |
|---|---|
| `preloadBook` | 인트로 영상이 **다 받아지면** 책 코드와 첫 장 그림을 받기 시작한다. 디코딩은 메인 스레드 밖에서 한다. 영상과 대역폭을 다투지 않는다 |
| `onNearEnd` | 영상의 마지막 1초에 책을 미리 마운트한다. 영상이 끝나자마자 읽을 수 있다 |
| 폰트 비동기 | 폰트 CSS가 첫 화면을 막지 않는다. 표지는 그림이고, 첫 글자는 영상 3초쯤에 나온다 |

| 측정 (9 Mbps) | 이전 | 이후 |
|---|---|---|
| 첫 화면 (FCP) | 0.69 ~ 1.17초 | **0.40초** |
| 가장 큰 요소 (LCP) | 4.46초 (폰트를 기다림) | **0.48초** |
| 영상 재생 시작 | 0.92 ~ 1.39초 | **0.77초** |
| 읽기 시작 | 8.7초 | **7.3초** |

| 읽기 시작 | 이전 | 이후 |
|---|---|---|
| 빠른 연결 | 6.8초 | **5.7초** |
| 데스크톱, CPU 4배 느림 | 9.1초 | **7.0초** |
| 휴대폰, CPU 4배 느림 | 8.1초 | **6.8초** |

영상 프레임 드롭은 그대로다 (302프레임 중 2~4개, 모두 재생 시작 순간).

## 5. 하지 않은 것과 이유

| 후보 | 기대 효과 | 하지 않은 이유 |
|---|---|---|
| MSAA 끄기 | −2.4 ms | 책 가장자리에 계단 현상이 보인다 |
| 카드의 투명한 부분 잘라내기 | 약 −0.3 ms | 카드 면적의 약 20%뿐이라 복잡도에 비해 작다 |
| 폰트 서브셋 직접 호스팅 | 약 −400 KB | 외부 폰트 파일을 받아 가공해야 하고, 나중에 글을 추가하면 글자가 빠질 수 있다 |
| 다음 장 카드 미리 마운트 | 넘김 시작 몇 ms | 구조 변경에 비해 이득이 작다 |
| 책등 모양 계산 최적화 | 약 50 ms, 한 번 | 페이지당 한 번이고 영상 뒤에서 일어난다 |

## 6. 확인한 것

- **테스트:** 56개 모두 통과 (`node --test tests/*.test.mjs`).
- **영상 → 책 전환 일치도** (평균 차이 /255, 낮을수록 같음):

  | 화면 | 일치도 | 비교 기준 |
  |---|---|---|
  | 데스크톱 | 2.0 ~ 2.4 | 이전 2.48 |
  | 휴대폰 390×844 | 3.2 | |
  | 휴대폰 375×667 | 1.9 | |

- **화면:** 세 장 모두 데스크톱·휴대폰에서 카드를 누르면 이야기가 열린다.
- **글로 읽기:** 열면 그리기 0, 닫으면 다시 초당 30번.
- **창 크기 변경:** 책상이 새 크기로 다시 그려지고 책과 정확히 겹친다.
